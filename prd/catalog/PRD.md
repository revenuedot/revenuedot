# Catalog (scope 1.6)

**Status:** Projects, apps, products, entitlements, offerings, packages, offering metadata and the current offering work through API v2 and the dashboard's Product catalog pages, and the SDK decodes the offerings they produce in the browser tests.

## Users and jobs
- **A developer setting up an app** adds the store product ids, groups them into entitlements such as `pro`, and builds the offering the paywall shows.
- **A growth person** changes which offering is current, or edits offering metadata, without shipping an app update.
- **A team moving from RevenueCat** recreates the same identifiers, so the SDK code in the app does not change.

## Essential now and later
Essential (Tier 1)
- Projects and apps, each app with a public SDK key that carries the store prefix the SDKs expect (`appl_`, `goog_`, `test_` and so on).
- Products by store identifier, with type, display name and an optional subscription duration; archive, unarchive and delete.
- Entitlements with attach and detach of products; archive, unarchive and delete.
- Offerings with a lookup key, display name, JSON metadata and exactly one current offering per project; archive and unarchive.
- Packages with reserved `$rc_` identifiers or custom ones, a position, and one product per app.
- Google Play eligibility on package products (`all`, SDK below 6, SDK 6 and above), so a legacy product and a new one can share a package.

Later
- Importing products from App Store Connect, Google Play and Stripe: built, see "Import from store" below.
- Store prices and review status, the product editor (CSV round trip to App Store Connect and Google Play) and "Create with AI": built, see the sections after "Import from store".
- Paywalls, targeting rules and experiments on offerings (Tier 2); web purchase links (Tier 3).
- In-app currencies and web discounts (Tier 2).

## RevenueCat behaviour we match
- Entitlements are the level of access a customer has; products unlock them ([Entitlements](https://www.revenuecat.com/docs/getting-started/entitlements), operations `attach-products-to-entitlement`, `detach-products-from-entitlement`).
- An offering is a set of packages, and the project has one current offering that the SDK returns as `current_offering_id` ([Offerings](https://www.revenuecat.com/docs/offerings/overview), fixtures `ios/resp-offerings-real-signed.json` and `android/get_offerings_with_placements.json`). The first offering in a project becomes current, like RevenueCat's default offering.
- Offering metadata is free-form JSON the app reads at runtime ([Offering metadata](https://www.revenuecat.com/docs/tools/offering-metadata), operation `update-offering`).
- Products are added by their store identifier ([Products overview](https://www.revenuecat.com/docs/offerings/products-overview), operations `create-product`, `archive-product`).
- The SDK's product-to-entitlement mapping lists both the bare Google product id and `id:base_plan` (fixtures `ios/resp-product-entitlement-mapping.json`, `android/product_entitlement_mapping.json`).
- Every v2 catalog response is validated against RevenueCat's OpenAPI v2 response schemas (operations `list-projects`, `create-app`, `list-products`, `create-entitlement`, `create-offering`, `create-packages`, `attach-products-to-package` and the rest of the catalog tags).

## Import from store
RevenueCat's Products page has **+ New → Import Products**, which lists the products of the connected store that can be imported ([Product configuration](https://www.revenuecat.com/docs/offerings/products-overview)). Google Play subscriptions are imported as subscription id plus base plan id, and one-time products only when they are backwards compatible; Stripe products are imported from the Product catalog with a price chosen when a product has several ([Stripe](https://www.revenuecat.com/docs/web/integrations/stripe)). App Store Connect needs a team key with the App Manager role ([App Store Connect API key](https://www.revenuecat.com/docs/service-credentials/itunesconnect-app-specific-shared-secret/app-store-connect-api-key-configuration)); Google needs "View app information and download bulk reports (read-only)" among the service account's permissions ([Play service credentials](https://www.revenuecat.com/docs/service-credentials/creating-play-service-credentials)).

What RevenueDot does (`apps/server/src/services/store-import.ts`, `routes/v2/store-import.ts`):
- `GET /v2/projects/{id}/apps/{app_id}/store_products` (extension) lists every store product, all store pages read, with `type`, `duration` (ISO 8601), `display_name`, the store's state, its group, `importable` with a `note`, and `in_catalog` plus the catalog `product_id`.
  - **App Store / Mac App Store:** the App Store Connect API key (`app_store_connect_api_key`, `_id`, `_issuer`): the app by bundle id, its subscription groups and each group's subscriptions (`subscriptionPeriod` → `P1W` … `P1Y`), and in-app purchases v2 (`CONSUMABLE`, `NON_CONSUMABLE`, `NON_RENEWING_SUBSCRIPTION`). Paging follows `links.next` only on App Store Connect's own host.
  - **Google Play:** the service account: `monetization.subscriptions.list`, one row per base plan as `subscription_id:base_plan_id` with the base plan's billing period (prepaid and installment plans noted), and `monetization.onetimeproducts.list` (falls back to the legacy `inappproducts.list` when that API answers 404) as `one_time`. A subscription without a base plan is listed but not importable. One-time products without a backwards-compatible purchase option are importable with a note (RevenueCat requires manual entry for them).
  - **Stripe:** the app's restricted key ("Products: Read" covers products and prices), through the outbound guard: one row per active price (`price_…`, the identifier web billing uses), named after its product; recurring prices become subscriptions with their interval, one-time prices non-consumables. A product without an active price and metered prices are listed but not importable. A price whose product id is already in the catalog counts as in the catalog. RevenueCat imports the Stripe product and picks one price; RevenueDot imports prices so a monthly and a yearly price of one product can both be in the catalog.
  - **Amazon:** 422 with the reason: Amazon has no API that lists in-app items, so they are added by SKU. **Test Store:** 422, its products only exist in RevenueDot.
- `POST …/store_products/actions/import` with `store_identifiers` (1–1000) and optional `entitlement_ids` re-reads the store, so type, duration and name always come from the store, never the request. It creates what is missing, reports what was already in the catalog (`existing`) and what failed (`not_in_store`, `not_importable`), and attaches every created and existing product to the entitlements. Running it twice changes nothing. Flat-rate Stripe prices also become web products, so the web checkout can sell them.
- Errors: 422 `unprocessable_entity_error` naming the missing credential or permission (App Manager role; "View app information and download bulk reports (read-only)"; Stripe "Products" Read), 422 `store_error` with `retryable: true` while the store cannot be reached, 404 for another project's app, 400 for an unknown entitlement id.
- Dashboard: "Import products" on the Products page (and "Import" on each app group) and on each app's page opens a dialog: app picker, the store's products with search, select all, rows already in the catalog disabled, store notes, an optional entitlement picker, and a summary of what was created, skipped and failed.

## Store prices and status
RevenueCat's Products list shows the store's price and period as each row's main label ("$89.99/year", "$3.99/week") with the identifier under it, and a Status column with the store's state ("Approved" after App Store review, the base plan's state on Google Play).

What RevenueDot does (`services/store-prices.ts`, migration 0030 `store_listings` and `store_listing_syncs`):
- **Read.** Refreshing an app reads every store product with its current price in every territory, its period and its state:
  - **App Store:** each subscription's prices (`GET /v1/subscriptions/{id}/prices`, `include=territory,subscriptionPricePoint`, all pages; the current price per territory is the one with the latest `startDate` that is not in the future), each in-app purchase's price schedule (`GET /v2/inAppPurchases/{id}/iapPriceSchedule` for the base territory, then `manualPrices` and `automaticPrices` of the schedule, all pages), and the review state (`MISSING_METADATA` … `APPROVED`). Territories are App Store Connect's three-letter codes (`USA`) and the currency comes with each territory.
  - **Google Play:** every base plan's `regionalConfigs` (region code, currency, price) and `otherRegionsConfig`, from the same `monetization.subscriptions.list` the import uses, the base plan's state (`ACTIVE`, `DRAFT`, `INACTIVE`), and one-time products' `regionalPricingAndAvailabilityConfigs` per purchase option (or the legacy `defaultPrice` and `prices`).
- **Cache.** One row per app and store identifier: type, period, store state, the base price (United States when the product has a price there, else the App Store base territory or the first region), every territory's price, and `refreshed_at`. One row per app records the last refresh, its outcome and the error. The cache is replaced as a whole on each refresh, so products deleted in the store disappear. The cache is not in project exports (the target reads the stores again); neither are product editor files, whose store writes are in the exported audit log.
- **When.** "Refresh prices" on the Products page and an app's product page (`POST /v2/projects/{id}/apps/{app_id}/store_prices/actions/refresh`, admins and developers; not in the audit log, it changes nothing in the project), the first time an admin or developer opens a page with an app whose prices were never read, every product editor download and upload, after every product editor commit, and the background tick once a day for apps whose cache is older than 24 hours (at most 5 apps a tick).
- **API.** `GET /v2/projects/{id}/store_prices?app_id=` (extension) lists cached store products with every territory's price and the refresh status per app. Products answer `indicative_price` (RevenueCat's field, `expand=indicative_price` or `items.indicative_price`) from the Test Store price, else the cached store price in the United States (`country: "US"`) or the base territory, else the Stripe web product's price. `expand=items.store_details` (extension) adds `store_details`: status, store state, base price and territory, number of priced territories, period, `refreshed_at`.
- **Dashboard.** Products rows show the price and period ("$89.99/year") over the identifier, and a Status column ("Approved", "Ready to submit", "Waiting for review", "In review", "Rejected", "Developer action needed", "Missing metadata", "Removed from sale", "Active", "Draft", "Inactive"). Each app group says where its prices come from and when they were read, with Refresh. The product page shows the store price, status and a "Prices by territory" table. The paywall editor preview reads `indicative_price`, so store prices fill `{{ product.price }}` where known (the Test Store price wins for Test Store products; samples fill the rest).
- **App Store Connect key.** Listing and changing prices needs an App Store Connect API team key with the App Manager role. RevenueDot's vault has only an In-App Purchase key, which App Store Connect refuses (401). The dashboard says so on the app group, the product page and the product editor, and links to the app's settings.

## Product editor
RevenueCat's Product editor (beta): "Update prices or create new products for the App Store and Play Store", in three steps: Update product file → Review changes → Commit to store. Step 1 picks the App Store or Play Store and the app, selects products ("0 selected of 15 products"; "Play Store one-time purchases aren't supported yet"), downloads a CSV, and uploads it after editing prices or adding rows (tabs Products and Files). Step 2 shows a diff of every price per territory and every new product. Step 3 commits to App Store Connect or Google Play and reports each row.

What RevenueDot does (`services/product-editor.ts`, `routes/v2/product-editor.ts`, dashboard `/projects/:id/product-catalog/product-editor`, migration 0030 `product_edits`, `product_edit_rows`):
- **CSV.** `GET /v2/projects/{id}/apps/{app_id}/store_products/export.csv?store_identifiers=a,b` (or `all=true`) answers one row per product and territory, base territory first, with the columns `store_identifier, display_name, type, duration, group, territory, currency, price, action`. Territories use the store's own codes (App Store `USA`, Google Play `US`); `price` is a decimal in the territory's currency (`9.99`, `1740` for yen); `action` is empty for existing products and `create` for a new one.
- **Upload and validation** (`POST /v2/projects/{id}/product_edits` with `app_id`, `file_name`, `csv`, at most 1 MB and 20,000 rows). The server re-reads the store (and refreshes the cache), then checks the whole file and reports every problem with its line: not a CSV or a missing column; an unknown product (`action` must be `create` to add one); `create` for a product that exists; an invalid price (not a number, zero or less, more decimals than the currency has, above 100,000,000); an unknown territory or a currency that is not the territory's; the same product and territory twice (both lines named); a new product without a name, type or period, or with conflicting values on its rows; types the store cannot create; Google Play one-time products ("not supported yet", like RevenueCat). Changes to the name, type, period or group of an existing product are ignored with a warning: the editor changes prices only.
- **Review.** A valid file becomes an edit with status `ready`: one row per changed price (current → new, change in percent, a new territory when there was no price), one group per new product, and the count of unchanged rows. An invalid file is kept with status `invalid` and its errors, so the Files tab lists it. Options: App Store subscriptions keep existing subscribers on their current price by default (`preserve_current_price`, Apple's `preserveCurrentPrice`); Google Play base plan prices apply to new subscribers, and existing subscribers keep their price until they are migrated in Play Console.
- **Commit** (`POST /v2/projects/{id}/product_edits/{edit_id}/actions/commit`). Rows are written through the existing store clients:
  - App Store subscription prices: the price point with that customer price in that territory (`GET /v1/subscriptions/{id}/pricePoints?filter[territory]=`), then `POST /v1/subscriptionPrices`. A price with no matching price point fails with the nearest price points named.
  - App Store in-app purchase prices: one `POST /v1/inAppPurchasePriceSchedules` per product with the base territory and every manual price (the existing ones plus the changed ones), so prices nobody changed stay as they are.
  - Google Play base plans: one `PATCH …/subscriptions/{id}?updateMask=basePlans&regionsVersion.version=2022/02` per subscription with the changed `regionalConfigs` prices; the rest of the subscription is sent back as read.
  - New products: App Store subscriptions and in-app purchases with the existing `create_in_store` logic (subscription group by reference name), then their prices; Google Play subscriptions with one base plan and its regional prices (`monetization.subscriptions.create`, or a `basePlans` patch when the subscription exists), then `basePlans.activate`. New products are added to the catalog, like an import.
  - Each row ends `succeeded` or `failed` with the store's message. Rows sharing one store call share its outcome. The edit ends `committed`, `partially_committed` or `failed`. A commit runs for at most 20 seconds and answers `committing` with the rows left; calling commit again continues. Two commits of one edit at the same time are refused (409). An App Store subscription or Google Play row whose store price already equals the new price succeeds without a write.
  - **Retry** (`POST …/product_edits/{edit_id}/actions/retry`) sets failed rows back to pending and commits them again.
  - **Audit log.** The upload, commit and retry are logged by the API's audit middleware (`product_edit_created`, `product_edit_commit`, `product_edit_retry`), and every committed row adds one entry (`store_price_changed`, `store_product_created`) with the app, territory, old and new price, the outcome and the edit id. The outcome is `succeeded` (written to the store), `failed`, or `unchanged`: an App Store subscription or Google Play price that the store already had (a retry, or a price set in the store after the upload), so nothing was written.
- **Roles.** Admins and developers (`project_configuration:products:read_write`) upload, commit, retry and discard. Viewers see the product list, download the CSV and read past edits. The CSV download needs `project_configuration:products:read`, like the other catalog reads (`GET /store_prices`, the import listing): it holds the territory prices `GET /store_prices` already returns to that scope. It reads the store live, so it also refreshes the cached prices; that changes nothing in the project, so read access is enough, while the explicit Refresh action stays with admins and developers (`read_write`). A secret key without the read scope gets 403.
- **Errors.** No App Store Connect key, an In-App Purchase key in its place, or a Play service account without "Manage store presence" are 422 with the fix; store outages are 422 `store_error` with `retryable: true`; an edit that is not `ready` cannot be committed (409).

## Create with AI
RevenueCat's "New product" and "New offering" menus offer "Create from scratch" and "Create with Rico" (AI).

What RevenueDot does:
- "New product" on the Products page and "New offering" on the Offerings page open a menu: **Create from scratch** (the existing dialog and form) and **Create with AI**. Create with AI asks what to create ("A monthly and a yearly Pro subscription on iOS and Android, and a lifetime unlock") and opens a RevenueDot AI conversation with that request.
- RevenueDot AI reads the apps, products and entitlements with its read tools and drafts the objects with two write tools: `create-products` (up to 50 products: app, store identifier, type, period, name, Test Store price) and `create-offering` (lookup key, name, packages with their products, optionally current). Each is one approval card listing everything it will write; nothing is written until the user approves, and Deny writes nothing. The tools call the API as the user, so roles, validation and the audit log (actor `assistant`) apply.
- The menu item is disabled with the reason when no model is configured, the project's AI setting is read only or off, or the role is Viewer.

## Test Store prices by currency
RevenueCat lets a Test Store product carry one price per currency and shows each customer the price in their currency. Its beta v2 endpoints (paths and scopes from the RevenueCat CLI's OpenAPI overlay, [`docs/specs/v2-beta-overlay.yaml`](https://github.com/RevenueCat/cli/blob/main/docs/specs/v2-beta-overlay.yaml); bodies from the CLI's client and tests, [`internal/api/products.go`](https://github.com/RevenueCat/cli/blob/main/internal/api/products.go) and [`internal/cli/project_setup_cli_test.go`](https://github.com/RevenueCat/cli/blob/main/internal/cli/project_setup_cli_test.go), commit `1fc0d5f`, 2026-10-02; the public [API v2 reference](https://www.revenuecat.com/docs/api-v2) does not list them yet):
- `GET /v2/projects/{id}/products/{id}/prices` (`project_configuration:products:read`): a bare JSON array of `{ id, currency, amount_micros }`. RevenueCat's MCP description says it works for Web Billing and Test Store products.
- `GET …/test_store_prices`: the same, marked deprecated.
- `POST …/test_store_prices` (`…:read_write`) with `{ "prices": [{ "currency": "EUR", "amount_micros": 8990000 }] }`: 201 and the created prices as an array. Test Store products only; other app types are an error.
- `PATCH …/prices/{currency}` (`…:read_write`) with `{ "amount_micros": 9990000 }`: the updated price. The CLI's `rc products prices set` creates missing currencies with POST and updates existing ones with PATCH.

What RevenueDot does (`apps/server/src/routes/v2/products.ts`, `services/test-store-prices.ts`, `packages/core/src/test-store-prices.ts`, migration 0042):
- **Storage.** `product_prices` holds one row per product and currency (`prc…` id, amount in micros). The product's `test_store_price_*` columns stay the **default price**, and every write keeps the default equal to one row. The migration copies each existing price into a row.
- **Endpoints.** The four above with the CLI's bodies; the default is listed first, then the others by currency. Currencies must be ISO 4217 codes RevenueDot can convert to USD and appear once per request. POST on a currency the product already has sets its amount (RevenueCat's behaviour there is not documented; an upsert keeps the CLI's create-then-patch flow working). PATCH on a currency without a price is 404. A product without a price gets USD as its default when USD is among the new prices, else the first one. Non-Test Store products are a 400 `parameter_error`. `GET …/prices` on a Stripe web product lists its Stripe price (`id` is the Stripe price id); other stores are a 400.
- **Extension:** `DELETE …/prices/{currency}` removes one currency (RevenueCat has no way to remove one; the dashboard needs it). Removing the default makes USD, else the first currency, the default; removing the last price leaves the product without one. The answer is `{ object: "product_price", id, currency, deleted_at }`.
- **Consistency and audit.** Each write runs in one transaction with the product row locked (`SELECT … FOR UPDATE`) and works on the product as it is then, so two writes at once cannot leave the default pointing at a missing row. PATCH is a plain update. The audit log names PATCH and DELETE of one price `product_price_updated` and `product_price_deleted` on the product, and the POST `product_test_store_price_created`.
- **The single price keeps working.** `test_store_price` on product create and update sets the default: it adds or updates that currency's row and keeps the others; `null` clears every price. `indicative_price` is the default.
- **Which price the SDK sees** (`GET /rcbilling/v1/subscribers/{id}/products` and the token form `/rcbilling/v1/customer/products`): the `currency` query parameter (purchases-js sends it), else the currency of the storefront country in `X-Storefront` (iOS sends the App Store storefront as alpha-3, Android its country), else of the country the customer was last seen in, else the default; USD 0 when the product has no price. The shape is unchanged.
- **What a purchase records.** The native SDKs post the price and currency they showed, which are stored as sent. purchases-js posts `price: null` with the currency: the price in that currency (or the store country's), else the default. `POST /v2/projects/{id}/test_purchases` without a `price` charges the price in `currency` or `country_code`'s currency, else the default.
- **Dashboard.** Edit product on a Test Store product lists one row per currency (currency, amount, remove) with a Default radio and "Add currency" (the next common currency not yet listed). Save checks every row (a missing amount, decimals the currency does not have, a currency listed twice), saves the default with the product, then adds, updates and removes the other currencies through the endpoints above. A row left as saved is kept as is, even with more decimals than the editor takes (a price set through the API). Adds and changes are compared with the server's latest prices, and only currencies the editor showed are removed, so a currency added elsewhere while it was open survives. When the prices cannot be loaded, the dialog says so with Retry, and Save keeps the name, type and duration and leaves the prices alone. The product page lists every price, the default first.

## Known gaps
- Store prices and the product editor need an App Store Connect API team key (App Manager role) for App Store apps; the vault has none yet, so App Store reads and writes are proven against fakes only.
- Changing Play prices needs the service account's "Manage store presence" permission, which the sandbox app's service account lacks; the real Play commit is proven up to Google's 403, and the write itself against the Play fake.
- The product editor changes prices and creates products; names, periods and groups of existing products, scheduled future prices, Apple's monthly plans for annual subscriptions and Play price migrations for existing subscribers are left to App Store Connect and Play Console. Play one-time products are not supported yet, like RevenueCat.
- Store import has run against the real Play Console (sandbox app). App Store Connect needs a team API key (App Manager role) that the vault does not have yet; Stripe has not run against a real account (no Stripe key in the vault).
- The offering Paywall tab is disabled.
- Google Play eligibility is kept and shown but can only be changed through `attach_products` in the API.
- The dashboard's "…" menu on each app group in Products is left out; the Apps page owns app settings.
